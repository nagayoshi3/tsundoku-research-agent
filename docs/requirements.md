# リサーチ・エージェント v1 要件定義書

2026-10-14 · @Nagayoshi Yamashita

## 1. 文書の目的と位置づけ

本書は、tsundoku-research-agent（LangGraph）の「何を、なぜ作るか」を定める要件定義書である。実装（`src/tsundoku/`）とテスト（`tests/`）を正とする。

| 文書 | 役割 | 読む人 |
|---|---|---|
| 要件定義書（本書） | 目的・スコープ・業務要件・非機能要件・受け入れ基準 | 作る人、仕様を確認する人 |
| 機能要件書（別紙） | 機能ごとの入力・処理・出力・例外・受け入れ条件、データ定義、設定項目 | 作る人、実装を任せるときの指示元 |
| README | 動かし方、出力、設定、コードの構成 | 動かす人 |

本書の記述がコードと食い違う場合は、実装とテストを優先し、本書を改訂する。

## 2. 背景と目的

毎週（または毎月）の論文・記事リサーチを、「何を読むか」の判断だけ人に残して自動化する。RSS リーダー（Inoreader）で「後で読む」に保存した記事はすでに自分が選んだものなので、テーマで絞り込まない。代わりに、同じ話題の記事を1件にまとめ、事前に与えた大きなカテゴリ（Physical AI、AIエージェント など）と重視キーワードで分類・並べ替えて、数百本を読める形に整理する。そのうえで LLM が話題を採点し、合計点が一定以上の話題（20件前後）を人が承認して、出典付きの Markdown 1ページにする。

| 目的 | 中身 | 満たせたと言える状態 |
|---|---|---|
| 自分のリサーチを楽にする | Inoreader で保存した記事を、同じ話題ごとにまとめてカテゴリ別に集計し、読むべき話題20件を提案させる | 週に10分以内の操作で、同じ話題が1件にまとまった出典付きのレポートが毎週出ている |
| 設計を学ぶ | エージェントのデザインパターンを、実際に動くコードで身につける | 必修パターン6つを、どこで何のために使ったか言える |

変えない方針は4つである。

1. 保存した記事をテーマで絞らない。カテゴリと重視キーワードは分類と並べ順にだけ使う
2. 何を読むかの最終判断は人に残す
3. 将来は要約ではなく「既知との差分」と「過去との関係」を出す（運用版）
4. 未解決の問いを翌週に渡す（運用版）

## 3. 用語定義

| 用語 | 意味 |
|---|---|
| 期間（period） | 処理対象の週または月。人は日付（2026-10-06 → その日を含む月曜〜日曜の週）、省略（直近の完了週）、-2（2つ前の週）で指定し、システムが内部の形に読み替える。内部の形は `2026-W41`（ISO 週、月曜0時〜翌週月曜0時、日本時間）または `2026-10` |
| 取得元（source） | 記事を読む先。Inoreader の保存済み記事。任意の RSS フィードも足せる |
| 候補（Candidate） | 取得元の形式を共通の形にそろえた記事1件（id、title、url、abstract、outlet、saved_at、tags など） |
| 話題（topic） | 同じ ID または同じ話題と判定した記事を1件（代表）にまとめたもの。まとめた記事は代表の `related` に残る。採点・承認②・レポートの単位 |
| カテゴリ（category） | 事前に与える大きな分類（初期値は9つ。第6章）。各話題に1つ付く。どれにも当たらなければ「その他」。絞り込みには使わない |
| 重視キーワード（focus_keywords） | 事前に与え、plan が数個足す語。採点に回す順番と採点の文脈に使う。絞り込みには使わない |
| 話題キーワード（keywords） | 記事ごとに抽出する、何の話かを表す一般語（VLA、world model など）。規則（重視キーワード・カテゴリの手がかり語の一致）と LLM で抽出し、クラスタリングと集計に使う |
| 固有名詞（entities） | 会社・製品・モデル名など。「どの対象の話か」を区別するためにクラスタリングで使う |
| 採点対象（pool） | 話題のうち、枠（max_items、通常100）で切って LLM の採点に回すもの。保存が枠より少なければ全話題 |
| 承認① | plan の提案（重視キーワード、採点件数）を人が確認・修正する停止点 |
| 承認② | 提示された話題（合計点がしきい値以上のもの全部。20件前後。設定で目安としきい値を変えられ、0 なら全件）から読まないものを除外し（残りは全部読む）、候補外から追加し、別々になった話題を1つにまとめる停止点。同じ話題かもしれない組はエージェントが推薦する。除外で目安を下回った分は次点で埋める |
| 次点 | 承認②で除外して確定が目安（20件）を下回ったとき、まだ提示していない話題を合計点の高い順に不足分だけ出すこと（backfill） |
| チェックポイント | LangGraph の SqliteSaver に保存された実行状態。thread_id は `weekly-2026-W41` のように期間から決まる |
| ガードレール | LLM の前後に置く検査。入力側は指示文らしき文の検出と区切り、出力側は出典の実在照合 |
| 指標（metrics） | 採用率、追加数、話題数、取得失敗数、ガード検出数など、毎回同じ形で残す数値 |
| 偽 LLM / サンプルデータ | API キーもネットワークも使わずに同じ流れを動かすための代替。デモと動作確認に使う |

## 4. スコープ

v1 は「Inoreader の保存済み記事を、週次・月次で同じ話題ごとにまとめてカテゴリ別に集計し、採点順に並べた話題を提示し、人の承認を経てレポートにする」までを対象とする。

| 区分 | 内容 |
|---|---|
| v1 の範囲 | Inoreader API（保存済み＝starred）からの取得と生 JSON 保存、期間による絞り込み、URL 正規化による重複除去、同じ話題のまとめ（埋め込み＋話題キーワード＋固有名詞）、話題へのカテゴリ付け、集計（日別・媒体別・タグ別・話題別・カテゴリ別・キーワード別・固有名詞別）と CSV/JSON 出力、重視キーワードによる並べ順と枠の配分、LLM による話題の採点（関連度・新規性・注目度、基準ごとの理由付き）と英語記事の日本語訳・要旨、合計点がしきい値以上の話題の提示（20件前後。カテゴリ別、同じ主語はまとめて提示）、承認①②（除外で目安を下回った分は次点で埋める）、停止・再開、ガードレール、読むと決めた話題の本文を読んだ要約（同じ話題の記事を横断、300字）と読まなかった話題の付録、指標付きレポート（Markdown と Word）と経路の記録、デモと動作確認 |
| 運用版に回す | 計画の2案化、クラスタのしきい値・辞書の調整ループ、承認②でまとめを解く操作（まとめる操作は v1 にある）、本文の深掘り（既知との差分）、知識グラフと既読除外、翌週への問いの受け渡し、3回採点の中央値、LLM による一部自動承認、Langfuse による費用計測、MCP サーバー化 |
| 対象外 | テーマによる記事の絞り込み（保存した時点で選んでいる）。UI、通知、毎日の収集。複数エージェントの役割分担・議論 |

複雑さの上限：LLM を使うステップ 4つ、承認 2つ、週をまたいで持ち越す状態 2つまで。パターンを足してもステップの数は増やさない。

## 5. 利用者と利用シーン

利用者は1名（リサーチを行う人＝システムを動かす人）。

| シーン | 頻度 | 人がすること | 時間の目安 |
|---|---|---|---|
| 週次リサーチ | 毎週月曜1回 | 起動（期間は省略で直近の完了週。過去の週はその週の日付を1つ渡す）→ 承認① → 承認② → レポートを読む | 合計10分以内 |
| 月次リサーチ | 毎月1回 | 同上（期間は前月） | 同上 |
| 中断と再開 | 随時 | 承認待ちで止め、後日同じ期間で呼び直す | — |
| 初回設定 | 1回だけ | Inoreader アプリ登録、API キーの設定、ブラウザでの許可、`check-inoreader` で日時項目の確認 | — |
| 再集計 | 随時 | 保存した生 JSON と CSV を使い、API を呼び直さずに別の切り口で集計する | — |

実行環境はローカルの Python または Google Colab。承認はテキストの入力欄で行い、専用の画面は作らない。

## 6. 業務要件

1回の実行で、数百件を「まとめて、分類して、並べて」から、読む数件に絞る。テーマでの絞り込みは行わない。LLM が関わるのは、記事ごとの固有名詞・話題キーワード・カテゴリの抽出と、話題の採点だけで、最終判断は人が行う。

| 段階 | 件数の目安 | 絞るのは誰か | やり方 |
|---|---|---|---|
| 集める | 期間内に保存した記事（週に数十〜数百本） | — | API で保存済みの一覧を読み、保存日時で今週・今月分に絞る |
| 話題をまとめる | 重複を除いた件数 | 機械（埋め込み＋話題キーワード＋固有名詞。LLM は抽出のみ） | 意味が近く、見出しの会社名・製品名が同じ記事を1件にまとめる。まとめた記事は「同じ話題: N本」として残す |
| 分類する | 件数は変えない | 機械（規則＋LLM） | 各話題に事前に与えたカテゴリを1つ付ける。当たらなければ「その他」 |
| 数える | 件数は変えない | 機械（LLM なし） | 日別・媒体別・タグ別・話題別・カテゴリ別・キーワード別・固有名詞別に数え、レポートとファイルに出す |
| 採点に回す | 最大100話題（保存が少なければ全部） | 機械（LLM なし） | 重視キーワードとの一致が多い順（同数なら多くの媒体が書いた話題、次に新しい順）。並べ順であって絞り込みではない |
| 提案する | 合計点がしきい値以上の話題を全部（件数では切らない）。しきい値は固定もできるが、初期値は自動で「上から20番目の合計点」を使い、同点まで含めるので20件前後になる。カテゴリ別に並べ、同じ主語の話題は1つにまとめて提示。除外で目安を下回れば次点を不足分だけ出す | LLM | 関連度・新規性・注目度（各0〜5）を基準ごとの理由付きで採点し、同じ話題を書いた媒体数の加点（最大3）を足した合計の高い順。同じ話題を書いた他の記事のタイトルも採点の入力に含める。記事を落とす判断ではなく並べ順 |
| 読む | 数件 | 人 | 読まないものだけを除外（理由付き）し、残りはすべて読む。候補外からの追加も可。レポートには採点した全話題がカテゴリ別に並ぶので、承認しなかった話題も後から読める |

人が止めるのは2か所。承認①は「範囲」（重視キーワードと採点件数）、承認②は「対象」（どの話題を読まないか、どれとどれを同じ話題として読むか）を決める。保存済みの記事はすでに本人が選んだものなので、承認②は選び直す場ではなく除外する場であり、何もしなければ提示分は全部読む。事前に与えたカテゴリと重視キーワードは、設定ファイルで維持し、毎回入力しない。

業務上の制約は次のとおり。

- 保存した記事はすべて話題に含め、テーマやカテゴリで落とさない。カテゴリに当たらない話題は「その他」として集計と採点に残る
- 同じ話題にまとめた記事は捨てず、承認②とレポートに「同じ話題: N本」と出典を出す（まとめの誤りに人が気づける）。自動のまとめが及ばなかった組は、承認②で人が1つにまとめられる（候補はエージェントが推薦し、まとめた話題は評価し直し、要約も横断して1つにする）
- 承認待ちの状態は保存され、日をまたいでも同じ期間を指定すれば続きから再開できる
- 読む本数は最初から固定せず、合計点が一定以上の話題を全部出す（20件前後が目安）。承認②で除外して目安を下回った分は次点で埋める。全部除外したときだけ、次点を出すか今回は終えるかを人が選ぶ
- 提案（plan）と人の確定（approved_plan）、提示・承認・却下理由・追加（feedback）は別々に記録し、後で「LLM の提案がどれだけ直されたか」を測れるようにする
- 本文を読むような費用のかかる処理（要約）は、承認②の後ろにしか置かない

カテゴリは次の9つを初期値とする（手がかり語は機能要件書 F-01）。最初の数週のレポートで配分を見て、統合・分割する。「その他」が3割を超えたら手がかり語かカテゴリが足りない。

| カテゴリ | 入るもの |
|---|---|
| Physical AI | ロボット学習、VLA、ヒューマノイド、sim-to-real |
| AIエージェント | エージェント設計、ツール利用、MCP、マルチエージェント、フレームワーク |
| RAG・知識活用 | RAG、GraphRAG、知識グラフ、検索、長文脈 |
| LLMモデル動向 | 新モデルの発表、スケーリング、アーキテクチャ、推論モデル |
| 学習・適応 | ファインチューニング、RL/RLHF/GRPO、蒸留、合成データ |
| 効率化・SLM | SLM、量子化、推論高速化、エッジ・オンデバイス |
| マルチモーダル | VLM、画像・動画・音声の理解と生成 |
| 評価・安全性 | ベンチマーク、評価手法、ガードレール、規制 |
| 産業・ビジネス | 資金調達、提携、製品発表、導入事例（業界ニュースの受け皿） |

## 7. システム化の方針

「集める → 選ぶ → 書く」の3段を LangGraph の11ノードで実現し、人は承認①②の2か所だけで止める。手順は LLM に作らせず、グラフで固定する（Single-path plan generator）。

処理の流れ：取得（並列）→ 同じ話題のまとめ → 集計 → 計画（キーワードの推薦）→ **承認①** → 枠 → 採点（並列）→ 選定 → **承認②** → 要約 → レポート。

取得（fetch_source）と採点（score_one）は Send で並列に起動し、次のノードで合流する。取得元が1つ失敗しても残りで先へ進む。承認で止まった状態は SqliteSaver に保存され、別のプロセスからでも同じ期間を指定すれば再開できる。

| 方針 | 内容 |
|---|---|
| 実行基盤 | Python 3.11 以上（ローカルの仮想環境、または Google Colab）。LangGraph 1.2.14、langgraph-checkpoint-sqlite 3.1.1、langchain 1.4.3、langchain-openai 1.7.0、feedparser、pydantic、requests、numpy |
| LLM | OpenAI（既定 `gpt-4.1-mini`、埋め込み `text-embedding-3-small`）。`init_chat_model` の「提供元:モデル名」形式で差し替え可能。temperature 0、Structured Output で出力の型を固定 |
| LLM を使う箇所 | 計画の提案（キーワードの推薦）、固有名詞・話題キーワード・カテゴリの抽出（25件ずつ1回の呼び出しでまとめて）、話題の採点（話題1件に1回）、確定した話題の要約（話題1件に1回）の4つ。クラスタリングの判定・集計・並べ順・上位選定・レポートは LLM を使わない |
| クラスタリングの手がかり | 埋め込み（意味の近さ）、話題キーワード（規則＋LLM）、固有名詞（どの対象の話か）の3つ。見出しの固有名詞が食い違えばまとめない |
| 状態 | ノード間のデータは State（JSON 化できる値のみ）だけを経由する。並列結果は `operator.add` で連結する |
| 外部との境目 | 取得元は「種類名 → 取得関数」の対応表（registry）に登録し、各取得関数が外部形式を共通の形 `Candidate` にそろえる（adapter）。取得元を足してもグラフは変えない |
| 安全 | LLM の前後に検査を置く。入力側は指示文の検出と `<paper>` による区切り、出力側は出典の実在照合 |
| 評価 | 作るときは `assert` による動作確認、動かすときは承認②の記録と指標を毎回残す |

必修デザインパターン6つ（Liu ら 2025 のカタログより）を v1 ですべて使う。

| パターン | 一言で | 使うステップ |
|---|---|---|
| Human reflection | 止まって、人が直して、再開する | approve_plan、review |
| Prompt/response optimiser | 指示と出力の形を固定する | plan、cluster_topics、score_one |
| Tool/agent registry | 道具を対応表から引く | fetch_source |
| Agent adapter | 外部の形式を内部の形にそろえる | fetch_source |
| Multimodal guardrails | 入るものと出るものを関所で検める | merge、score_one、report |
| Agent evaluator | 毎回同じ形で測って残す | review、report |

## 8. 機能要件の概要

機能は17個。各機能の入力・処理・出力・例外・受け入れ条件は機能要件書（別紙）に定める。

| ID | 機能 | 概要 | モジュール |
|---|---|---|---|
| F-01 | 設定とキー管理 | スイッチ、CONFIG（カテゴリと手がかり語、重視キーワードを含む）、API キーの探索 | `config.py` |
| F-02 | 計画の提案（plan） | 取得・まとめ・集計の後に動き、その期間の記事によく出ている語から重視キーワードに足す語を最大3個、理由付きで推薦し、採点件数を提案する。絞り込みはしない | `prompts.py`、`nodes/planning.py` |
| F-03 | 承認①（approve_plan） | 提案を人が確認・修正。与えたキーワードは必ず残る。提案と別キーに記録 | `nodes/planning.py` |
| F-04 | 取得元の対応表と並列取得（fetch_source） | 取得元ごとに Send で並列、失敗は2回まで再試行して記録 | `sources/__init__.py`、`nodes/fetch.py` |
| F-05 | Inoreader 取得 | OAuth 認証、保存済み一覧のページ取得、生 JSON 保存、期間での絞り込み、Candidate への変換 | `sources/inoreader.py` |
| F-06 | 同じ話題のまとめと分類（cluster_topics） | URL 正規化による同一 ID の統合、固有名詞・話題キーワード・カテゴリの抽出、埋め込み＋キーワード＋固有名詞による同じ話題の統合 | `nodes/cluster.py` |
| F-07 | 集計（aggregate） | 日別・媒体別・タグ別・話題別・カテゴリ別・キーワード別・固有名詞別の集計と CSV/JSON 出力 | `nodes/aggregate.py` |
| F-08 | 枠の配分（merge） | 重視キーワードの一致数で並べ、取得元ごとの枠で採点対象を切る。入力側ガード | `nodes/fetch.py` |
| F-09 | 話題の採点（score_one） | 話題1件（代表＋同じ話題の他の記事のタイトル）につき LLM を1回呼び、関連度・新規性・注目度（0〜5）と基準ごとの理由・総評、日本語タイトル・要旨を得る | `nodes/scoring.py` |
| F-10 | 上位選定（shortlist） | 合計点（関連度＋新規性＋注目度＋媒体数）がしきい値以上の話題を全部選ぶ。しきい値は自動（上から目安20番目の点。同点まで含む）か固定。次点は「目安−確定済み」を未提示から。カテゴリ別に並べて提示 | `nodes/scoring.py` |
| F-11 | 承認②（review） | カテゴリ・基準ごとの点数と理由・同じ話題の本数付きで提示し（同じ主語はまとめて）、除外（理由）・追加・まとめ（同じ話題かもしれない組の推薦付き。まとめた話題は採点し直し、要約は横断）を受け付け記録。除外で目安20件を下回った分は次点で埋める。全除外時は次点か終了かを聞く | `nodes/review.py` |
| F-12 | レポート（report） | 集計（カテゴリ別を含む）・確定した話題・却下理由・選定の記録・指標を Markdown 1ページにして保存 | `nodes/report.py` |
| F-13 | ガードレール | 入力側（指示文検出・無害化・区切り）と出力側（出典の実在照合） | `guardrails.py` |
| F-14 | 状態保存と再開 | SqliteSaver によるチェックポイント、interrupt / Command(resume) による停止・再開 | `nodes/planning.py`、`nodes/review.py`、`graph.py`、`cli.py` |
| F-15 | 対話実行（run_interactive） | 起動・再開・完了済みの判定、入力欄による承認①② | `cli.py` |
| F-16 | デモと動作確認 | サンプルデータで入力なしに最後まで通るデモと、`assert` による確認 | `tests/` |
| F-17 | 要約（summarize） | 読むと決めた話題の本文を取りに行き、同じ話題の記事を横断して300字（複数本は400字）に要約する。読まなかった話題も付録に要約する（設定で切替） | `nodes/summarize.py` |

## 11. 前提条件と制約

- 実行環境はローカルの Python または Google Colab。Colab ではランタイムが切れると作業フォルダが消えるため、保存先を Google ドライブにする
- Inoreader は Pro プラン（API 利用可）を前提とする
- 入力は Inoreader で「後で読む」に保存した記事で、保存した時点で本人が選んでいる。したがってシステムは絞り込まず、整理と提案に徹する
- カテゴリとその手がかり語、重視キーワードは設定（`config.yaml`）で事前に与える。「その他」が多ければ手がかり語を足す
- Inoreader の「保存した日時」に当たる項目（`timestampUsec` / `crawlTimeMsec` / `published`）は公式の説明で確かめられていない。初回に `tsundoku check-inoreader` で実データを見て `date_field` を決める
- 話題のまとめのしきい値（`SAME_TOPIC = 0.62` など）はデモのサンプルと偽の埋め込みで確かめた値。本番の埋め込みと LLM のキーワードでは最初の数週で調整する
- まとめと採点の対象はタイトルと要旨（Inoreader の `summary.content`、2,000字で切る）。本文は、読むと決めた話題の要約のときだけ取りに行く
- 時刻は日本時間（Asia/Tokyo）で扱う。週は ISO 週（月曜始まり）
- 指示文の検出は決まった言い回しの正規表現であり、言い換えにはすり抜けられる。防御は「検出・区切り・人の承認」の三重で行う

## 13. リスクと対処

| リスク | 対処 |
|---|---|
| Inoreader API の回数制限（1日100回） | 1回の実行は数回。期間より古くなったら読むのを止める。生 JSON が残るので集計し直しに API は要らない |
| 保存日時の意味が想定と違う | 初回に実データで確かめ、違えば `date_field` を切り替える |
| 同じ話題のまとめを誤る | まとめた記事は捨てずにレポートと承認②に出す。見出しの会社名・製品名が違えばまとめない。しきい値と辞書で調整する |
| 取得や LLM の呼び出しが不安定 | 取得元ごとに再試行して記録し、残りで進む。デモはサンプルデータで |
| 採点が安定しない | 基準と例を固定。再現性を測り、駄目なら3回採点の中央値 |
| 外部の文章に LLM への指示文が紛れ込む | 区切ってデータとして渡し、検出して記録。出典は機械で照合 |
| 承認待ちの状態が消える | 状態（SQLite）の複製を Google ドライブなどに置ける |
| 週次の運用が続かない | 承認は合計で週に10分以内。調整するのは提示する本数と採点の基準 |
| パターンを足しすぎて複雑になる | ステップ数の上限は変えず、導入の目安を満たすまで足さない |

## 14. 今後の拡張（運用版）

v1 を自分のリサーチに2〜3週使い、困ったことが起きた部品だけを足す。困っているかどうかはレポートの指標と承認の記録で判断する。

| 足すもの | 導入の目安 |
|---|---|
| 計画の2案化（Multi-path plan generator） | 承認①でキーワードを毎回大きく直している。記事の集計が週次で安定して回っている |
| 3回採点の中央値（Voting-based cooperation、条件付き） | 同じ入力で順位が大きく入れ替わる |
| 本文の深掘り（Incremental model querying、Self-reflection） | 比較実験で精度が上がる |
| 知識グラフと既読の除外（RAG） | 過去の論文との関係をレポートに出す |
| 費用の計測、翌週への問いの受け渡し（Proactive goal creator）、Inoreader への書き戻し | すべてが週次で回る |
| 承認の記録を評価データにした LLM による判定（Cross-reflection） | 人との一致率が十分な範囲だけ承認を緩める |
| MCP サーバー化 | 取得元と知識グラフを他のエージェントから使える |
